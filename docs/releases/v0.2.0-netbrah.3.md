# speedread 0.2.0-netbrah.3 — the MCP server reads any path it is given

A pre-release of the [netbrah fork](https://github.com/netbrah/speedread/blob/v0.2.0-netbrah.3/docs/FORK.md) of [speedread](https://github.com/brennengreen/speedread) by Brennen Green, based on upstream `37abea2` (0.1.0 plus four commits). MIT, like upstream.

> **Not yet run on macOS.** Both macOS binaries were cross-compiled on Linux and have never been executed on a Mac. The two Linux binaries were run before release (x86_64 natively, arm64 under QEMU). Treat the first install on a Mac as the first test, and please report what happens.

## What changed since 0.2.0-netbrah.2

- **`speedread mcp` no longer answers `Outside the workspace`.** However it is started — by a plugin, by the Claude Desktop bundle, or registered by hand as `speedread mcp` or `speedread --root DIR mcp` — it reads any path a call names. Its roots (`--root`, the launch directory, `CLAUDE_PROJECT_DIR`, the client's folders) say where relative paths and path-less calls resolve, and nothing else. A path-less `search` still covers only those folders, and a server with no folder still refuses a path-less call rather than walk the disk.
- **Behaviour change: `--root DIR` no longer confines a server.** If you registered `speedread --root DIR mcp` to keep it inside `DIR`, add `--restricted`: `speedread --restricted --root DIR mcp` behaves as before. `--unrestricted` is still accepted, so existing configurations start unchanged.
- **Commands are as before.** `speedread read|search|trace|map|symbols` stay limited to their roots unless given `--unrestricted`.
- **Every refusal says how to lift it.** `map`, `search`, `trace` and the JSON commands used to give only the path.
- **Fixed** (introduced in 0.2.0-netbrah.2): a fenced server with no folder told the model to use absolute paths, then refused them.
- **Plugin skill.** Where a host starts no local server (Perplexity Computer), the skill runs the command line; it now passes `--unrestricted`, so that route reads by absolute path too.

Why, and what is given up: [docs/specs/08-unfenced-server.md](https://github.com/netbrah/speedread/blob/v0.2.0-netbrah.3/docs/specs/08-unfenced-server.md). In short, the fence bought little — the agent hosts that run speedread already give the model a shell or a file reader of their own — and it produced refusals that depended on how and where the server happened to be launched. The server is read-only either way; it now reads whatever your account can, limited by the host's own permission prompts and the operating system.

The reading, searching and tracing code is otherwise unchanged from 0.2.0-netbrah.2.

## Install

Full instructions: [docs/DISTRIBUTION.md](https://github.com/netbrah/speedread/blob/v0.2.0-netbrah.3/docs/DISTRIBUTION.md).

| Host | How |
|---|---|
| Claude Code | `claude plugin marketplace add netbrah/speedread#v0.2.0-netbrah.3` then `claude plugin install speedread-netbrah@netbrah-speedread` |
| Claude Cowork | Customize > Plugins > upload `speedread-netbrah-plugin.zip` |
| Claude Desktop chat | open `speedread-aarch64-apple-darwin.mcpb` (Apple Silicon) |
| Cursor | copy `plugins/speedread-netbrah` into `~/.cursor/plugins/local/` and reload |
| Grok Build | `grok plugin install netbrah/speedread@v0.2.0-netbrah.3#plugins/speedread-netbrah --trust` |
| Perplexity Computer | Plugins > Add custom > Import plugin from GitHub > `https://github.com/netbrah/speedread/tree/v0.2.0-netbrah.3/plugins/speedread-netbrah` |

Upgrading: a plugin installed from `main` picks this up when the host updates it (`claude plugin update speedread-netbrah@netbrah-speedread`; reinstall for Grok); the launcher then downloads this release's binary on first use. For Claude Desktop, open the new `.mcpb`. The plugin and the bundle already started the server unfenced in 0.2.0-netbrah.2, so for them this release changes only the refusal messages and the skill's command-line route. The change matters to a server registered by hand.

It installs as **speedread (netbrah fork)**, beside upstream's rather than over it. Both offer tools named `map`, `read`, `search` and `trace`, so enable one at a time.

The macOS binaries need macOS 11 or later; the arm64 one is ad-hoc signed, neither is notarized. If macOS refuses a file after a browser download: `xattr -d com.apple.quarantine <file>`. A download made by `curl`, which is what the launcher uses, is not normally quarantined.

## Command line

```sh
mkdir -p ~/.local/bin
curl -fsSL https://github.com/netbrah/speedread/releases/download/v0.2.0-netbrah.3/speedread-aarch64-apple-darwin.tar.gz | tar -xz -C ~/.local/bin
speedread --version   # speedread 0.2.0-netbrah.3
```

Replace `aarch64-apple-darwin` with `x86_64-apple-darwin`, `x86_64-unknown-linux-musl` or `aarch64-unknown-linux-musl`.

To register it by hand: `{ "command": "/path/to/speedread", "args": ["mcp", "--no-cwd-root"] }`.

## What was tested

Before publication, on Linux x86_64 (2 vCPU sandbox):

- **Source.** `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` (Linux, and again for `aarch64-apple-darwin`), and all 99 tests pass. One new test starts a server four ways (`--root DIR mcp`; `mcp` inside a project; no subcommand; `mcp` in `/`) and checks that each answers `map`, `read`, `search` and `trace` on a sibling directory, that a path-less `search` still covers only the server's folder, that `--restricted` refuses all of them without leaking file contents, and that the `map` command is still refused outside its folder. It was seen failing before the change. Six deliberate breakages of the new code each made a test fail.
- **Before and after, on two real repositories.** The 0.2.0-netbrah.2 binary, started as `speedread mcp` or `speedread --root DIR mcp` in a ripgrep checkout, refused `map`, `read` and `search` on a zod checkout beside it. This release answers all three in both configurations, and refuses them with the new message under `--restricted`.
- **Linux binaries.** Both are static (no interpreter, no shared libraries). The x86_64 binary run natively and the arm64 binary run under QEMU gave byte-identical output to the tested build on 17 commands over the ripgrep source (`map`, `map --symbols`, three kinds of `search`, `trace` callers/implementations/callees, `read` by path, symbol, line range and heading, `symbols`, JSON output, a refused and an `--unrestricted` read outside the folder, `--version`). Each, started as an MCP server three ways (`mcp`; `mcp --unrestricted --no-cwd-root`; `--restricted --root DIR mcp`), read outside its folder in the first two and refused in the third.
- **macOS binaries.** Inspected, not run: correct CPU type, minimum macOS 11.0, only system libraries linked, arm64 ad-hoc signed. The binary inside the `.mcpb` is byte-identical to the one in the arm64 tarball; the bundle's manifest has no `user_config` and starts `mcp --unrestricted --no-cwd-root`.
- **Launcher.** 11 checks (`scripts/test-launcher.sh`) under `sh`, `dash` and `bash` against a local mirror, as in 0.2.0-netbrah.2. `shellcheck` clean.
- **Manifests.** `claude plugin validate` (plugin, marketplace and the unpacked zip), `grok plugin validate`, Cursor's `validate-template.mjs`, and the Agent Plugins 1.0.0 JSON schemas all pass.

Not tested: anything on macOS; Claude Desktop and Claude Cowork (no way to run either here); Cursor at runtime (its command line needs a login to manage plugins, so only the manifest validator ran); Perplexity's import dialog. Installs from this tag in Claude Code and Grok Build, and the launcher against the published files, are run after publication and recorded in [docs/specs/07-distribution.md](https://github.com/netbrah/speedread/blob/main/docs/specs/07-distribution.md).

## Known limits

- The macOS builds have only been compiled and inspected, as above.
- A server started in `/` or a home directory, whose only folder comes later from the client's roots, still says in its opening instructions that no folder is configured. Calls resolve against the client's folders once they arrive; only the sentence is stale.
- The binaries were built from this tag's parent commit; the tag adds only the checksums in the plugin launcher and documentation (`scripts/fork-release.sh` explains why).
- The plugin's first use needs network access to github.com. `SPEEDREAD_BIN`, `SPEEDREAD_NO_DOWNLOAD` and `SPEEDREAD_RELEASE_URL` are the ways around that.
- Not listed in any curated directory (Anthropic's, Cursor's, the MCP Registry). Those need the repository owner's sign-in; the steps are in docs/DISTRIBUTION.md.
- Limits carried over from 0.2.0-netbrah.1: content after a line longer than 4 MiB is not text-searched (the answer names the files); a working set larger than `--cache-mb` is re-parsed on access; a whole-tree request on a Chromium-sized tree can hit the 10 s deadline and say so (`--deadline-ms 30000` waits longer).
